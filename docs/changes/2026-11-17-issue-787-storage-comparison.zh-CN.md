## Cloudflare 免费档：限制、已测规模和估算分开

截至 2026-11-17，**尚未验证本候选在 Workers Free 上的稳定数据量极限**。维护者要求后续先本地验证，因此没有为取得容量数字访问云端 D1。已有本地结果不能证明单请求 CPU、每日计费读写或生产迁移达标。

| 约束 | 当前口径 |
| --- | --- |
| 既有产品单表上限 | 2,000 条记录、40 个字段；本候选未提高该上限 |
| D1 Free 单库 | 500 MB；账号合计 5 GB、最多 10 个库。当前默认单 DB 绑定不会自动把账号容量聚合或分片 |
| D1 Free 每日额度 | 读 5,000,000 行、写 100,000 行；扫描和索引维护也计入，不能按返回条数或操作次数直接换算 |
| Workers Free | 每日 100,000 请求，HTTP 单请求 10 ms CPU；等待数据库的时间不等于 CPU |
| 附件 R2 Standard | 每月 10 GB-month 免费存储、100 万 Class A / 1,000 万 Class B 操作；独立于 D1 容量 |

来源：[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[D1 计量](https://developers.cloudflare.com/d1/platform/pricing/)、[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)、[R2 价格](https://developers.cloudflare.com/r2/pricing/)。D1 还限制每行/字符串 2,000,000 字节、每条 SQL 100 KB、100 绑定参数、函数 32 参数、LIKE/GLOB 模式 50 字节；本次补充了显式配置 50 字节模式上限的本地回归，长 UTF-16 边界筛选仍可使用。

当前本地规模覆盖 2/10/30 张各 1,000×10 表，以及两张 1,950×38 富文本表。下面是对应版本的空间事实及纯算术演示，不是云端支持承诺：

| 合成数据 | 已测总记录 | 完整实验库 | 其中共享候选对象 | 500,000,000 字节按完整库线性外推 | 仅按候选对象外推 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 30 张 1,000×10 | 30,000 | 153.19 MiB | 50.87 MiB | 约 9.3 万条 | 约 28.1 万条 |
| 两张 1,950×38 富文本 | 3,900 | 166.10 MiB | 44.10 MiB | 约 1.1 万条 | 约 4.2 万条 |

完整实验库含旧正文迁移输入和基础对象；候选对象含记录、初始历史、FTS、主键/唯一索引及受控字段索引，排除了上述旧正文和基础对象。候选对象数字不能冒充整个数据库大小。以 500,000,000 字节演示 `预算 × 已测记录数 ÷ 已测字节`，并非精确解释供应商 MB 单位；也未按外推规模造数。实际可用空间必须扣除普通笔记、保留旧正文、更多历史、索引及其他对象；多表索引增长也可能偏离线性。附件正文占 R2，但附件元数据仍可能占 D1。

因此，当前能确认的是上述本地规模与既有单表约束，**不能把 30,000 条当作极限，也不能把 9.3 万/28.1 万等空间估算标成“免费档已支持”**。稳定极限须按代表性数据、历史和访问频率，在获准的隔离环境验证 CPU、累计读写、迁移/备份及公开表单，取最先触达的约束。计算输入与来源指纹见[容量及对照数据](evidence/2026-11-16-shared-records/capacity-and-physical-comparison.json)。

## 冻结物理表方案的设计

每张逻辑表对应一个服务端命名的物理表。小目录保存工作区、表、字段 ID 到真实列的映射、字段类型、视图和修订；数字/布尔/日期/文本使用真实列，附件数组保留 JSON。显示名变化只修改元数据，不改列名。筛选、排序、游标和按页输出共用查询编译逻辑，列到响应 JSON 的组装成本纳入测量。

值与存储兼容时优先改元数据；需要转换时分配影子列，只分批处理目标字段，准备相关索引和搜索投影。预检有失败值就阻止发布；表示变化需确认。执行时该表停写、旧值可读，完成后原子切换映射及依赖。取消与旧列回收需校验任务/列所有权，不能误清理已复用的列。原物理表首版曾将跨类型历史回放列为未实现边界；这是当时的实现范围，不是物理表模型的固有限制，不否定维护者另行完成的历史测试。

其价值是更紧凑的标量存储及单表索引维护隔离；代价是真实列分配、DDL、影子列、取消/回收与映射版本的一致性。共享记录方案省去这些物理列生命周期步骤，仍须维护事务、索引、搜索与历史。

## 历史同条件性能对照

以下是冻结实验中**同一轮、同输入**的共享 JSON 部分索引与物理表对照，不能与当前共享候选的不同版本、历史覆盖及指标直接横比。运行环境为本地 Bun 1.3.14 / SQLite 3.54.0 / arm64，不是网页、网络、Workers CPU 或 D1 账单。

最初结构对照（每表 1,000×10，每表一个数值视图索引）：

| 逻辑表数 | JSON 部分索引数据库 | 物理表数据库 | 改普通字段 VM 步数：JSON / 物理 |
| --- | ---: | ---: | ---: |
| 2 | 2.539 MiB | 2.277 MiB | 60 / 34 |
| 10 | 8.977 MiB | 7.762 MiB | 132 / 34 |
| 30 | 25.098 MiB | 21.426 MiB | 312 / 34 |

这组写入只是存储层探针，不含完整鉴权、搜索和历史事务；VM 指令成本也不同，不能将 312/34 解释成用户保存快 9 倍。全局 JSON 表达式索引在 30 表时占 47.949 MiB，其中视图索引 24,000 KiB；部分索引与物理表的视图索引均为 600 KiB，支持排除“所有字段都建覆盖全库的索引”作为默认设计。见[原始结构对照](evidence/2026-11-16-shared-records/physical-record-baseline.json)。

D1 参数/SQL 限制修复后的同轮查询服务中位耗时（ms，包含元数据和响应组装）：

| 查询 | JSON 部分索引 | 物理表 |
| --- | ---: | ---: |
| 1,950×38：数值索引排序首屏 | 0.126 | 0.251 |
| 1,950×38：下一页 | 0.145 | 0.255 |
| 1,950×38：索引可判空的范围外查询 | 2.904 | 0.115 |
| 30 表：数值排序首屏 | 0.108 | 0.115 |

范围外物理查询采用额外的索引判空计划，JSON 对照未采用同一优化，因此差异不能全部归因于布局；OR、未索引条件等仍可能扫描。见[兼容性修复对照](evidence/2026-11-16-shared-records/physical-query-review.json)。后续物理表无筛选单选排序将 JSON 组装延后到当前页，1,950×38 的含 UTF-8 编码中位数由 0.692 降至 0.423 ms，普通数值排序基本不变（0.164 → 0.163 ms）。这是物理实现自身的优化，不能与上表跨轮拼成结构间加速比。见[归因及优化结果](evidence/2026-11-16-shared-records/physical-query-attribution.json)。

当前共享候选另有 32 组同库完整分页对照：已复现的临时单选/数字组合在宽表上由 3,758,012 降至 277,995 条 VM 指令，约减少 92.6%。该值只与自身旧查询比较，不与上述单次耗时或物理方案比较。综上，保留物理方案的空间与写入隔离证据，同时采用更符合当前维护需求的共享记录方向；两者都不能仅凭本地结果宣布免费档稳定可发布。
