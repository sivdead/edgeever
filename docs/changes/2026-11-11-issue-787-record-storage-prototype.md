# #787: shared-record storage candidate

## Problem, basis and current decision

#805 remains based on `a18db6a4`, limited to named views and the existing compatible performance improvements. Storage changes proceed separately. Following the [maintainer's feedback](https://github.com/tianma-if/edgeever/pull/805#issuecomment-6874868531), this candidate uses shared record tables, separate metadata and controlled field indexes. Each record stores cell JSON, scoped by `workspace_id` and `table_id`; inserting a row or editing a cell does not rewrite the table document.

See [capacity and design comparison](2026-11-17-issue-787-storage-comparison.md) for official Free-plan constraints, tested scale, storage arithmetic and matched historical physical-table comparisons. Space extrapolation is not a cloud acceptance guarantee.

The independent physical-table, real-column and shadow-column implementation is suspended. Its original worktree and evidence remain intact. Earlier shared-JSON experiments, the query compiler and strict type converter may be reused; physical-table results do not validate this candidate. All work uses local synthetic data, with no cloud D1 access, deployments or free-quota consumption.

Parsing retains this optional metadata through generic edits, view-format changes, serialization and Markdown/ZIP export/reimport, preserving unchanged nulls. Ordinary unmarked legacy documents retain existing parsing/editing semantics without automatic marking or relaxed API validation. CSV visible-value export gains no new lossless protocol.
7. Write meaningful integration tests before implementation. Then run targeted integration tests, root/mobile typechecks and the Web build; check the complete diff against this list. Supply a reproducible local driver, current design, code locations and evidence.

## Temporary combined-sort fix and acceptance

The reproduced blocker is an unsaved select-group plus numeric secondary sort: the existing numeric index is not reused, and wide-table pagination repeats scans/sorts, costing about 3.76 million local VM instructions. Reuse the query compiler's finite-group capability and an existing secondary index with matching direction. A select-only sort can page within groups by original position; a select plus one indexed field can continue by group and indexed keys. Temporary queries add no indexes, caches, schema, services or client state.

Query-plan and shared-JSON-layout changes may produce disjoint streams ordered by select option rank, secondary value and position, materializing at most 51 candidates per page. Equal secondary values seek by value and position; subsequent values and nulls use separate streams to avoid rescanning ties. Each stream fills only remaining page capacity. Payload lookups must be scoped by workspace and logical table as well as position.

Retain field types, legacy/OR filters, sort direction, nulls last, stable ordering, 50-record pages, cursor identity/revision checks, one exact count on the first filtered page and no persistent indexes for temporary queries. Select the optimized plan only when an existing suitable index/group prefix is available. Other valid queries retain their existing path, with no new rejection or product capacity limits. Arbitrary text and other combinations without any suitable sort index need separate evaluation; SQL rewriting alone is not claimed to remove all repeated scans.

First reproduce cumulative-work growth using complete 500/1,000-row pagination, then implement. Doubling data should produce approximately linear cumulative SQLite VM work instead of row-count times page-count growth. Validate nulls, large tie groups, both directions, OR, omitted totals, other tables sharing positions, stale cursors and bindings. Compare against the same existing wide-table database and captured baseline SQL, including payloads, count frequency, storage and indexes. Risks are missing/duplicate rows, incorrect null order and cross-table payload lookups; validate full results and cursors. Rollback removes only the new query branch, without migrating storage.

## Correctness and recovery contract checks

Local review covers shared-record reads/writes, query indexes, type jobs, history, explicit snapshot import and their actual local consumers. Existing performance/product-integration boundaries remain. These repairs follow reproduced failures and existing parsing/transaction contracts, without new capacity limits, Unicode rejection, caches or retries.

- Preserve accepted record/field/table identities through native UTF-16 binding and decoding, avoiding duplicate writes and count corruption. Build cursors from complete logical sort keys rather than lossy database-bound text. Existing text truncation can produce isolated surrogates; valid stored values must still paginate. Reuse client sort-key semantics for text and attachments.
- Preserve legal field IDs such as `__proto__`, `constructor` and `toString` as ordinary cell keys. Parsing/normalization read only own properties and retain existing missing-cell defaults; constructing cells must not invoke the prototype setter. Validate shared storage, explicit snapshot export/reparse and missing values rather than rejecting these IDs to bypass reproduced data loss.
- Normalize new null attachment search values as arrays and recognize old empty-string projections from authoritative nulls without backfill, so legacy contains/eq never pass an empty string to json_each. Preserve logical nulls. Represent NUL-containing SQL option/text constants losslessly, without new rejection rules.
- Preserve existing JavaScript UTF-16 contains semantics for text and attachment filenames, including matching one half of a supplementary character. Ordinary needles keep instr; only leading-low/trailing-high surrogates require extra byte-aligned matching. Remove placeholder replacement that incorrectly treated question marks inside table IDs as parameters; identities remain data.
  D1 limits LIKE/GLOB patterns to 50 bytes. Exclude the longest literal anchor already checked by instr from GLOB and verify only short boundary patterns on either side; long needles remain accepted. Validate with a local SQLite connection explicitly configured to that limit, not its host default. This does not establish Workers CPU acceptance.
  Legal combinations of 40 long field IDs, 40 options, eight filters and full ordering can also exceed D1's 100 KB SQL limit. Use equivalent shorter JSON `->>` option extraction for nonindexed select sorting, retaining existing index expressions and parameter reuse without reducing accepted fields/options/filters. Replay full pagination with SQL/binding/function/pattern limits applied together and recheck cumulative query work.
- Recheck visibility inside initialization transactions and leave no candidate on failure. Successful acknowledgements report their own committed revision rather than a later writer’s state. Recheck preflight job state inside start transactions so stale requests cannot revive cancelled jobs. Persist only diagnostic identifiers required for execution, not full source/target columns in one JSON state cell; return complete diagnostics to callers.
- Compare field identities exactly rather than with locale equality. Reuse the parser's existing 80-character record-ID contract to prevent accepted rows from becoming unreadable in logical exports.
- Atomically refresh current search projections after field-name/order changes without changing cells or adding unchanged record history. Read records once using bounded position pages; view-only changes do not rebuild unrelated projections.
- Commit explicit snapshot/history import atomically. Invalid later input or a database failure must not expose the first historical snapshot as a finished current table or prevent retry. Reuse initialization/replacement statement planning, without extra persistent jobs.
- Remove unused physical-table layout options, unreachable SQL and a generic placeholder-replacement layer with no actual parameters, retaining ordinary keyset, indexed-select and grouped plans. Validate semantics and costs with existing regressions and same-database comparison, not line-count reduction.

## Current-snapshot and historical-read scope and acceptance

An unspecified-revision full snapshot pins its starting head and pages current records by workspace/table/position, returning at most 51 per page. After each data read it checks revision/visibility. Concurrent edits, deletion, restoration or type publication invalidating that head return the existing 409 rather than mixing values, retrying automatically or falling back to a history scan. Type preparation before publication leaves revision/current values unchanged and old values readable. Current snapshots do not depend on unrequested history counts or repeat counts per page.

Explicit-revision snapshots and snapshotPage retain immutable record-history reconstruction, including an explicitly requested current revision, so later writes do not change historical content. This iteration adds no retention policy, cleanup or persistent checkpoints. This path still depends on relevant history size, and exporting all history costs more as requested history grows; measure it separately rather than applying the current-snapshot budget. Future pruning/checkpoints require a separate recovery-contract decision.

First reproduce lost encoding and history-dependent current reads. Validate all field nulls, generic edits, view upgrades/legacy projection, generic serialization and existing small ZIP reimport, preserving unmarked semantics; also test concurrent writes/hiding during current reads, explicit history and cross-type restoration. Compare complete-snapshot/current-document-export VM work, pages, returned rows and counts locally for empty tables and 100/200/400 records, with 1/10/50 revisions. Current-document exports exclude additional history. Fixed-size current reads must not grow approximately linearly with history, and doubling records/pages should produce near-linear work. Risks are changed nulls or mixed concurrent snapshots; validate values, concurrency and budgets. Rollback removes parser/read changes without schema/data migration. Local evidence does not establish cloud CPU/billing or production backup integration. Full-history archives and production request scheduling need separate budgets.

## Boundaries, risk and rollback

Do not change ordinary notes, #805, the main workspace or the suspended physical-table worktree. Production automatic migration, sync queues, client pages, public-form routes and default backup entry points do not switch in this iteration. The candidate runs through an explicit local driver and must not be presented as a released fix. Existing native capabilities, permissions and resource quotas are not relaxed.

Field metadata currently supports rename/reorder with row search maintenance; field addition/removal is not implemented. Offline protection is a whole-table revision conflict, not per-record/cell merging. Actual queue reconnection, cross-type old drafts and lost-response retries remain integration gates. The candidate's global Unicode ordering is unchanged by this repair; its effect on existing editors is a separate compatibility boundary before production integration.

Main risks are tenant leakage, overwritten concurrent changes, mismatched historical schemas/cells, stale indexes and moving full-table costs into history or pagination. Validate transactions, revision gates, historical snapshots and cumulative query costs. Rollback means stopping the local candidate and retaining the original baseline; no production data migrates. Cloud CPU/quota, production client integration, cross-platform upgrades and production migration/rollback remain separate acceptance work.
